# Changelog

Nothing in this repository has been tagged. Nothing has been uploaded to PyPI.

## Unreleased

- **The bridge now needs gotdms `v0.2.0`** (`290bb791b00ad56edeee814960062107d0600cc8`); `go.mod` requires it. Protocol 2 reads with `dataset.WithSharedClock` and values-only reads with `dataset.WithoutTimes`, and neither is in `v0.1.2` or earlier, so the bridge no longer builds against an older core. `v0.2.0` also brings the core's durable-write, torn-tail and float64 span-read changes; this package does not use `WithSync` or `WithLenientTail` yet.
- **Protocol version 2; version 1 is gone.** The client and the bridge ship together, so neither side keeps a v1 path. A version 1 bridge (an old `GOTDMS_BRIDGE` build) is refused with a `ProtocolError` that says to rebuild it. Request frames are unchanged. A data reply (`read`, `read_many`, `read_values`) is now `result_begin` (channels, clocks, and the exact size of every Arrow stream), `part` frames of at most 64 MiB, and `result_end`. There is no 4 GiB limit on a reply any more: a 4.48 GB single-channel read went through end to end on a test machine (not in CI). See `docs/nptdms-migration.md`.
- Each distinct time axis is sent once, as one `time_ns` column, and each channel names its clock by id. A channel sends `y`, plus `relative_s` only when the bridge was asked for relative time. (Clocks and channels are packed into few streams; see below.) Channels on one clock get the same `time_ns` numpy array object. Clocks are shared when they come from one timestamp channel, one waveform axis, or are equal sample for sample; the bridge never assumes. `as_polars(align="strict")` skips the comparison for channels that share one clock. The bridge reads with `dataset.WithSharedClock` and writes each column straight from the series' slices into part frames, without building the reply in memory. On the 4-channel, 5M-sample float64 fixture (medians of 3 processes), `read_all()` sends 200 MB instead of 320 MB; Python's peak above baseline is 227 MB instead of 352 MB, the bridge's peak RSS is 369 MB instead of 1,772 MB, and the call takes 0.47 s instead of 1.58 s.
- A read with `absolute=False, relative=False` reads with gotdms `dataset.WithoutTimes`, so the bridge builds no time axis for it. Offset/limit and DAQmx reads, which need times to order merged samples, drop them before the reply is encoded. On the 4-channel, 5M-sample fixture (medians of 3 processes) the bridge's peak RSS for that read went from 369 MB to 169 MB (the core's float64 span read without a second copy accounts for part of it, and the default read went from 369 MB to 209 MB). A values-only read of one timed int16 waveform channel of 560M samples (4.48 GB of float64) peaked at 5.62 GB in the bridge and 4.54 GB in Python; with a time axis that read had reached about 12 GB.
- **Many channels are packed into few Arrow streams.** Each protocol 2 stream has one schema and one or more record batches, and every channel and clock is a column named by `stream`, `batch`, and `column` (and a channel's `relative_column`) in `result_begin`; `streams[]` entries add `batches`. Channels of the same length and column layout are columns of one batch (up to 16 such lengths, most channels first); the rest share one "ragged" stream per column layout, one batch per channel. A shared stream holds at most 16 MiB; a larger channel has its own. `read_values` packs the same way. Before, every channel was its own stream, so a full read of a file with many short channels paid a schema message, an Arrow writer, a part frame, and a Python `open_stream` per channel. The bridge also indexes the catalog by channel name once per open dataset: it used to copy the whole occurrence list several times per selected channel, which made a read of n channels O(n²) and was most of the bridge's time on a 785-channel file. Python reads fixed-width columns with `np.frombuffer` views instead of `to_numpy`, and `read_tdms` builds numeric and timestamp Polars series from those views, so it no longer imports `pyarrow.compute` (about 40 ms per process) unless a file has string or bool channels. The bridge stages small writes into parts of up to 1 MiB instead of 64 KiB. On a synthetic 785-channel file of 1,000 float64 samples per channel in 10 segments (medians of 7 fresh processes on a Linux test machine), `open` plus `read_all()` took 69 ms, against 193 ms with unbatched protocol 2, 266 ms with protocol 1, and 47 ms for npTDMS `TdmsFile.read`; `read_tdms` took 55 ms instead of 114 ms. With 100 samples per channel in one segment, `open` plus `read_all()` took 56 ms instead of 170 ms (npTDMS 24 ms). About 22 ms of that is `open`, which batching does not change. The 4-channel, 5M-sample fixture is unchanged (each channel is over 16 MiB, so it keeps a stream of its own), and so are its memory peaks. The client checks that every column is named once and that each named column has the expected name, type, and length.
- `open` is cheaper on wide files. The catalog is compact on the wire: file paths and channel property pairs are sent once and rows refer to them by index (`property_table`). Data replies refer into that catalog for each channel's `files` and `properties` and for `reads[].file` instead of repeating them. The client expands both, so `Session.open`, `Session.catalog`, `Channel.properties`, `properties_match`, `Series.meta`, and the `reads` of `read_channels` return what they did; a bad index raises `ProtocolError`. `describe`, `find`, `search`, `match`, and `convert` bundles are unchanged. The bridge parses each file's metadata while the dataset layer indexes the same files, instead of afterwards; a file whose size or modification time changed by the end of the open is parsed again. Core `v0.2.0` gives the bridge no access to the files it already parsed, so each file is still parsed twice; that needs a core change. Expanded rows, `Series.meta`, and `reads` keep their keys in the order they always had. `properties_match` compares interned property ids instead of encoding each file's properties as JSON on every read. On the 785-channel, 1,000-sample fixture (medians of 11 fresh, interleaved processes), the catalog is 275 KB instead of 429 KB, and the `read_all` header is 413 KB instead of 616 KB. `open` takes 18 ms instead of 20–22 ms, and `open` plus `read_all()` takes 53–56 ms instead of 60–67 ms (npTDMS `TdmsFile.read` 46–48 ms). With 100 samples per channel, the same steps take 43–45 ms instead of 51–56 ms (npTDMS 23 ms). Opening a directory of 16 such files takes 155–163 ms instead of 185–193 ms. The 94-channel and 4-channel fixtures are unchanged within noise, and the bridge's peak is at most 0.3 MB higher on single files and not higher on the 16-file directory.
- **On Windows the package now depends on `tzdata`** (Apache-2.0, `tzdata; sys_platform == 'win32'`, the same requirement as Polars' own `timezone` extra). Every time column this package returns (`read_tdms` timestamp channels, the `time` column of `as_polars` and `scan_tdms`) is `Datetime("ns", "UTC")`, and Polars turns those values into Python datetimes (`to_list`, `rows`, iteration) through `zoneinfo`. Windows has no system IANA database, so without `tzdata` those calls panicked with `ZoneInfoNotFoundError: No time zone found with key UTC`. The column types are unchanged. The Windows CI job installs `tzdata` too, and a test checks that `UTC` loads.
- An error after `result_begin` ends the reply with `result_end` carrying the error. The client raises it and the session stays usable. The bridge never sends more bytes of a stream than `result_begin` declared, so a stream that comes out longer than its size is such an error too, not a desynchronized pipe. A reply that stops without `result_end` (the bridge died, a framing fault, or `KeyboardInterrupt` during the read) kills that bridge, and the session then raises `ProtocolError` instead of reading a desynchronized pipe. `read_tdms` does the same for its short-lived bridge.
- Pipe writes and reads loop until every byte has moved. Unbuffered pipes can move fewer bytes per call than asked, and Windows caps one call near 2 GiB. On Linux and macOS each pipe read and write waits in `poll` first, so `KeyboardInterrupt` (Ctrl+C, or a Jupyter interrupt) reaches a read that is blocked on the bridge. Without it, importing Polars, which installs a `SIGINT` handler with `SA_RESTART`, made that read uninterruptible until the bridge sent more bytes. On Windows a blocked pipe read still sees the interrupt only when it returns. In a console Ctrl+C also stops the bridge, which ends the read.
- `GOTDMS_BRIDGE_PART_BYTES` (an integer from 1 to 67108864, that is 64 MiB) lowers the bridge's part cap, for tests. It cannot raise the cap; any other value makes `gotdms-bridge serve` exit with status 2 before reading a request.
- Building a wheel or sdist fails if `go.mod` replaces gotdms with a local directory, in a `replace` line or a `replace ( ... )` block. The wheel's `go build` runs with `GOWORK=off`, so a `go.work` file cannot swap in a local core either.
- `convert` bundles keep their layout: each `.arrow` file still carries its own `time_ns`. `gotdms_bridge` in `manifest.json` is now `2`.
- `read`, `read_many`, `read_channels`, and `read_all` default to `relative=None`, which means `not absolute` (was `relative=True`), so the bridge sends one time column instead of two. **Public API change.** With absolute time on (the default), `Series.relative_s` is still there: it is computed in Python from `time_ns` and `basis` on first access, bit-for-bit what the bridge's Go `RelativeTimes` returns. `relative=True` computes it during the read. `absolute=False` alone, as before, returns `relative_s` (and now no `time_ns`). `absolute=False, relative=False` sends sample values only, and `relative_s` is then `None` for a timed channel. `as_polars`, `scan_tdms`, and `Channel.time_track` request only the time column they use. The bridge's own `relative` default is unchanged.
- Read responses are read with `readinto` into preallocated, 8-byte-aligned buffers and decoded through `pyarrow.py_buffer`, so fixed-width columns are aligned views of those buffers instead of copies. With protocol 2 (above) each Arrow stream has its own buffer. Short channels share a stream (above), so keeping one keeps at most 16 MiB of other channels alive; a channel over 16 MiB has a stream of its own and keeps only its samples and its clock. Before protocol 2, on a 4-channel, 5M-sample float64 read, this took `read_all()` from 480 MB to 320 MB sent and Python's peak above baseline from about 1,468 MB to about 352 MB; protocol 2's numbers are above.
- CI runs the Python tests at the minimum supported versions (Python 3.10, numpy 1.26.0, pyarrow 14.0.0, polars 2.0.0) in a job named `Test at minimum supported versions (Python 3.10, numpy 1.26, pyarrow 14, polars 2.0)`. Every CI install of npTDMS, the LGPL-3.0-only test oracle, is pinned to `nptdms==1.13.0`.
- A bad TDMS file raises `CorruptFileError` (code `corrupt`) from `open`, `scan_tdms`, and `read_tdms`. That covers a wrong segment tag, an unsupported version, a corrupt structure, and a truncated file. Before, `read_tdms` and append-mode `write_tdms` raised `ArgumentError` and `open` and `scan_tdms` raised `GotdmsError` with code `error`. `CorruptFileError` subclasses `GotdmsError`. A missing path is `ArgumentError` from all three; before, `open` and `scan_tdms` raised `GotdmsError` with code `error` for it. The bridge sends the new code.
- A `Session` that is dropped without `close` stops its bridge process when it is garbage collected (`weakref.finalize`). Before, the stderr thread kept the session alive and the process ran until the interpreter exited. At interpreter exit the finalizer does not write to a bridge that another thread is still reading from; it closes stdin and the bridge exits. `close` and `with` are still preferred.
- Bridge stderr kept for error messages is capped at the last 64 KiB per process.
- `read_tdms` on Python 3.10 no longer fails on a timestamp property whose fraction is not 3 or 6 digits (for example `.25`). Python 3.10 `datetime.fromisoformat` rejects those.
- Doc fixes: EXTRACTION.md no longer says gotdms still has `bridge/`; missing-dependency messages no longer name extras that do not exist; the client docstring says each channel's stream carries its own time columns.

- The gotdms pin moved to `v0.1.2` (`8d2f134a160600c8a12b2076cc395c6b05c5c9e2`). Files with metadata padding between the object list and the raw-data offset, such as NI HSAI DAQmx captures, now open.
- Require `github.com/trey-copeland/gotdms` `v0.1.1` (`7d514a7710d8ed18f3884a78c19e4cfcbe2b32a8`). That tag is `v0.1.0` (`622cb34bacb80fd810d46ee77183e2bae80bf52d`) plus the fix for `ReadValues` and `Group.Values` when an interleaved channel continues in a later segment. This package was not affected: `read_tdms` reads each channel with `Channel.Values`, and `open`, `read`, and `scan_tdms` read through the dataset layer, which also reads each channel on its own. A regression test now covers interleaved channels that continue in a later segment on all of those paths. This package does not build segment-index sidecars. gotdms `v0.1.1` writes those sidecars as version 2, and a reader built with gotdms `v0.1.0` treats a version 2 sidecar as a miss.

## 0.1.0 (unreleased)

First packaging of the Python client and the `gotdms-bridge` binary. `0.1.0` is the version in `pyproject.toml`. It is not a git tag.

- Interactive `serve` protocol version 1 and `convert` bundles, Arrow IPC.
- `scan_tdms` returns a Polars `LazyFrame`. `describe` reads catalog metadata and does not decode samples. `read` and `read_many` take optional `offset` and `limit` and report `reads` and `limited`. Protocol version stays 1.
- `write_tdms` writes one or more Polars groups to a TDMS file: file, group, and channel properties (including `unit_string` and explicit integer widths), waveform properties, string channels, and channels whose lengths differ. `read_tdms` reads those samples back in the stored type. `Session.read` stays float64. Fixed-size columns use `Writer.Stream`. Create replaces the destination only after the file reopens. Append adds a segment when the existing file ends on a finished segment. Protocol version stays 1 (`write_begin`, `write_chunk`, `write_end`, `read_values`).
- Write and read fixes from review. A failed or interrupted append truncates the file back to its original length. Before this fix it left a partial segment that readers returned and later appends refused. Create mode follows the umask, so it no longer forces 0600, and replacing a file keeps its mode. Replacing a file never deletes the destination first. On Windows the move is retried briefly instead. NaN and infinite float properties no longer stop the bridge in `open`, `scan_tdms`, or `read_tdms`. A result header that cannot be encoded, or a payload over 4 GiB, is now an error reply.
- Polars frames via `as_polars`. numpy arrays for raw samples. Pandas is not a dependency. npTDMS is not a dependency. CI installs it only as a reader of files this package wrote.
- Wheels embed one platform binary. Source distributions ship `go.mod` and `go.sum` and do not vendor gotdms. `go build` resolves `github.com/trey-copeland/gotdms` at the version required in `go.mod`. See Unreleased.
- DAQmx raw channels are read. Index words `0x1269`, `0x1369`, and `0x126A` become the primary scaler's stored type. Digital lines are uint8 0/1, which Polars reads as `UInt8`. `open`, `read`, `read_tdms`, and `scan_tdms` keep those values raw unless `scaled=True`. `scaled=True` applies the DAQmx linear or polynomial chain (`DAQmxScaledFloat64s`) and returns float64. A channel with no DAQmx scale raises `NoScaleError`. An unsupported scale type raises `NonlinearScaleError`. `NI_Scaling_Status` of `scaled` means the stored samples are already engineering units, so `scaled=True` returns those values as float64. Ordinary channels still apply only an NI linear scale. The column is the primary scaler. Writing a DAQmx raw index is not supported. Protocol version stays 1.
